# StreamHub 单体版与微服务版性能对比

## 1. 结论

在本机、同一 PostgreSQL、同一批数据、同一压测器和相同参数下，每个接口每个版本实跑 3 次。主对比 18 个测量全部为 HTTP 200，错误率均为 0%。

本次没有测出“微服务性能提升”。在此单实例和资源限制下，微服务版三个接口的平均吞吐量都更低，应用容器总内存约为单体的 2.86–2.91 倍。微服务的收益是业务隔离、独立部署和扩缩容，不是本组小规模请求下的单请求性能。

## 2. 公平性控制

| 控制项 | 实际做法 |
|---|---|
| 机器 | 同一 Windows / Docker Desktop 主机，同一时段顺序执行 |
| 数据库 | 同一个 `streamhub-perf-postgres` 容器 |
| 数据 | `public` 单体表迁移到三个服务 Schema，行数和内容摘要强制一致 |
| 顺序 | R1 单体→微服务；R2 微服务→单体；R3 单体→微服务 |
| 压测器 | 同一 `scripts/performance_load.py` |
| 预热 | 每个测量 5 秒 |
| 读取接口 | 并发 4、持续 20 秒、超时 10 秒 |
| 登录接口 | 并发 4、持续 30 秒、超时 10 秒 |
| 应用资源 | 单体 0.5 CPU/512MiB；每个业务服务 0.5 CPU/512MiB；Gateway 0.25 CPU/128MiB |
| 数据持久化边界 | 基准 PostgreSQL/MinIO 使用 tmpfs；不读写或删除日常业务卷 |

微服务拥有三个业务进程，但某一接口的活动业务服务与单体都限制为 0.5 CPU。资源列按整个后端应用求和：单体为 monolith；微服务为 Gateway + user/content/social。PostgreSQL 单独列出。MinIO 不参与三个接口，未计入资源汇总。

## 5. 三轮范围与差异

| 接口 | 版本 | 吞吐量三轮范围 | 平均响应三轮均值 | P95 三轮均值 |
|---|---|---:|---:|---:|
| 分类列表 | 单体 | 67.000–69.705 | 58.710 ms | 102.193 ms |
| 分类列表 | 微服务 | 47.676–48.863 | 82.588 ms | 183.903 ms |
| 最新视频列表 | 单体 | 15.232–20.361 | 218.504 ms | 399.680 ms |
| 最新视频列表 | 微服务 | 8.982–14.079 | 339.155 ms | 679.057 ms |
| 登录 | 单体 | 0.892–0.954 | 4246.404 ms | 4702.404 ms |
| 登录 | 微服务 | 0.900–0.909 | 4401.777 ms | 4699.154 ms |

以三轮均值计算，微服务相对单体：

- 分类：吞吐量低 28.99%，平均响应时间高 40.67%，P95 高 79.96%。
- 视频列表：吞吐量低 33.86%，平均响应时间高 55.22%，P95 高 69.90%。
- 登录：吞吐量低 3.11%，平均响应时间高 3.66%；P95 低 0.07%，差异小到不应解释为提升。
- 应用总内存高 186.27%–190.73%；应用平均 CPU 高 81.67%–106.12%。

只有 3 轮，且视频列表波动明显，不能把百分比写成普遍规律或统计显著结论。

## 6. 为什么有差异

1. 分类接口没有跨业务服务调用，但微服务多经过一次 Nginx Gateway 和一次容器网络转发，因此仍有固定延迟和 CPU 成本。
2. 视频列表在 content-service 查询后，还调用 user-service 批量补充上传者摘要；单体在一个进程和数据库关系内完成。额外 HTTP、JSON 编解码与调度使吞吐下降、尾延迟升高。
3. 登录主要耗时是相同 bcrypt 密码校验，所以 Gateway 的固定成本占比小；两版吞吐和 P95 接近。
4. 微服务版常驻 Gateway 和三个业务进程，即使部分服务在该接口中空闲，也保留解释器、连接池、探针和框架内存，因此总内存明显更高。
5. PostgreSQL 共用且数据很小；数据库不是唯一瓶颈。读取接口中应用 CPU接近限制，更像应用序列化/代理/跨服务开销。

## 7. 并发 16 过载对照

同一读取脚本另以并发 16 运行 3 轮。分类和登录仍可完成，但微服务视频列表三轮均触发 Gateway 的 2 秒上游超时：

| 版本 | 吞吐量 req/s | 成功吞吐量 | 平均 ms | P95 ms | 错误率 |
|---|---:|---:|---:|---:|---:|
| 单体 | 16.508 | 16.508 | 965.900 | 1431.420 | 0% |
| 微服务 | 7.902（均为失败响应） | 0 | 2016.227 | 2062.574 | 100% |

因此并发 16 不是微服务正常工作区间，不能把 7.902 req/s 当作业务吞吐。该结果说明 HPA 生效前或单实例部署下，视频列表需要容量保护、缓存、查询/序列化优化，或调整经验证的超时与副本策略。

## 10. 限制与下一步

- 数据集只有 3 用户、10 分类、18 视频，不能代表百万行查询。
- 单实例 Compose 对比没有启用 HPA；第 3 项 HPA 实验是另一组实验，不能混合结果。
- Docker Desktop 受宿主机调度影响；已交替版本顺序并报告范围，但没有消除所有噪声。
- `docker stats` 约每 1–2 秒采样，适合课程对比，不是精密性能剖析。
- 若要改善微服务视频列表，应先剖析 content→user 调用、响应序列化和缓存；不能只加大超时掩盖容量问题。
